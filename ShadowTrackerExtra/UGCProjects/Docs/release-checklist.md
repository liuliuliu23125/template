# 发布、真机与匹配检查清单

> 面向 Agent 的“上线前检查 + 人工步骤清单”。Agent 不能点编辑器/管理后台，但可以核对工程配置、解释失败原因、产出操作步骤。
> 官方来源：项目设置、上传工程与真机测试、玩法提审与更新、匹配设置、二次匹配、阶段匹配、局内补人、PIE 失败排查。

## 何时读

- 玩法开发完成，准备测试上传、真机测试或提审。
- 匹配进不去、人数不对、补人失败。
- 上传失败、PIE 启动失败、版本不匹配。
- 需要给人工一份可执行的发布清单。

## 1. 工程配置

| 项 | 位置 | 说明 |
|---|---|---|
| 初始地图 | 工程设置 | 对应 `.ugcproj` 的 `StartMapName` |
| GameMode | 工程设置 | 对应 `GameModePath` |
| 队伍数 / 每队人数 | 匹配设置 | 决定大厅丢入对局的玩家数 |
| 匹配方法 | 匹配设置 | `PeaceClassic`（经典段位）/ `Random` / `UserDefined` |
| 多模式 | 匹配设置 | 默认单模式；多模式建议 4 个，不超过 6 个 |
| 阶段匹配 | 匹配设置 | 梯度降低成局人数；单阶段 <20 人 |
| 补人 | 匹配设置 + 代码 | `SetPlayerFill` / `OpenPlayerJoin` |

- `.ugcproj` 的 `[MatchSetting]` / `[MultiModeSetting_N]` 是这些配置的落盘结果；改配置优先用编辑器 UI。
- 多模式必须有一个默认模式；模式解锁条件只是展示，实际解锁逻辑要自己写。
- 调试多模式：调试选项勾选「子模式调试」并填正确的 SubModeID；填错会进默认模式。

## 2. 测试上传 vs 发布上传

| 方式 | 用途 | 关键限制 |
|---|---|---|
| 测试上传 | 快速真机测试 | 不能在管理平台绑定项目 |
| 发布上传 | 正式提审/上架 | 才能绑定项目；记录 jobid |

- 白名单最多 30 个 UID；测试人员需加入白名单。
- 编辑器版本与客户端安装包版本至少前两位一致。
- 真机测试用开发 APK：`安卓/` 下的安装包，不是正式服。
- 真机测试环境 10 秒会强制匹配进对局；正式服会凑满人数。
- 绿洲启元模式需账号等级 5 级；不够可用大厅 GM 加经验。

## 3. 真机测试步骤（人工）

1. 设置白名单（UID 从开发客户端头像/用户信息复制）。
2. 测试上传工程，选择 Windows / Android / iOS 平台。
3. 安装 `安卓/` 下的开发 APK，登录。
4. 大厅进入绿洲启元，找到工程，下载并进入。
5. 需要模拟上架状态时用发布上传，并在管理平台绑定项目、开启测试。
6. 验证后关闭测试。

## 4. 提审与更新（人工）

1. 发布上传，记录 `jobid`。
2. 管理平台 → 项目管理 → 玩法项目列表 → 添加新项目（名称/分类/标签/开发者）。
3. 添加新版本，选择上传工程与 `jobid`。
4. 上传图标/封面/详情图/视频：图片 jpg，视频 mp4/avi，规格按页面要求。
5. 完成侵权自查，提交审核。
6. 更新：上传新版本 → 更新提审 → 填写版本更新说明 → 侵权自查 → 提交。

> 项目名称和开发者创建后不可改；分类/标签可改。

## 5. 匹配规则

- 匹配方法：
  - `PeaceClassic`：用经典段位分。
  - `Random`：完全随机。
  - `UserDefined`：自定义分，初始 2000、最低 0、最高 4000，每 100 分一段，默认 10 秒扩一段、最多 ±10 段。
- 队伍数 ≠ 局内实际分队；例如匹配 1 队 9 人，进局后再自行分 6v3。
- `RequestMatch` / `RequestCancelMatch` 不能同帧调用，有 1 秒限频。
- 阶段匹配时长由官方统一：前两阶段各 5s、第三/四阶段各 2s、之后 1s。
- 真机测试有 30 秒保底：匹配不到会强制拉入符合条件玩家。
- 阶段匹配下玩法必须适配不同开局人数；单阶段 <20 人。

## 6. 局内补人

流程必须按顺序：

1. `UGCGameSystem.OpenPlayerJoin` 开启补人（持续生效）。
2. `UGCGameSystem.ApplyPlayerJoinLimitCount({ [TeamID] = 需求人数, ... })` 申请。
3. 达到人数自动停止；或 `StopPlayerJoin` 手动清空所有请求。

规则：

- 匹配池人数必须 ≥ 申请人数，否则不生效。
- 第一次补人申请后 30 分钟未完成，匹配池清空。
- 某模式连续 1 小时无新玩家，匹配池清空。
- 补人总人数不能超过玩法最大玩家数（队伍数 × 每队人数）。
- 启用阶段匹配时，上限按人数最多的阶段计算。
- 补人进来的是玩法内队伍关系，不是大厅队伍关系。

## 7. 上线前检查清单

- [ ] `.ugcproj` 的 `StartMapName` / `GameModePath` 指向正确资产。
- [ ] 队伍数 × 每队人数与玩法实际分队逻辑一致。
- [ ] 多模式有默认模式，模式 ID 与代码一致。
- [ ] 阶段匹配各阶段人数递减，且都能正常开局。
- [ ] 补人申请人数与测试客户端数匹配，避免测试时被保底拉走。
- [ ] 白名单已配置，测试人员 UID 正确。
- [ ] 编辑器/客户端版本前两位一致。
- [ ] `ReferenceAssetList` 无失效资源、无跨工程引用。
- [ ] 上传前清理无用资源，避免 Cook OOM。
- [ ] PIE 能启动，无 `PIE debug failed` / `DS Failed`。
- [ ] 真机跑过一局完整流程（登录 → 匹配 → 对局 → 结算 → 退出）。
- [ ] 提审素材格式/尺寸正确，侵权自查已完成。

## 8. 高频失败对照

| 现象 | 优先排查 |
|---|---|
| 上传失败 | `ReferenceAssetList` 失效/跨工程引用 → 资源过大 OOM → DataTable RowStruct → Shader |
| PIE 启动失败 | 搜 `PIE debug failed`，按关键字对照（次数/权限/SubMode/文件名/DS 路径） |
| DS 启动失败 | `DS Failed!`，看 DS 日志中的工程逻辑错误 |
| 匹配不进 | 队伍数/人数、匹配方法、阶段匹配、白名单、版本 |
| 补人失败 | 是否先 `OpenPlayerJoin`、匹配池人数、30 分钟/1 小时超时、人数上限 |
| 版本不匹配 | 编辑器与客户端前两位版本号 |

## Agent 规则

1. 不声称“已上传/已提审成功”；这些是人工步骤，Agent 只能核对配置与日志。
2. 先检查 `.ugcproj` 与 `ReferenceAssetList`，再解释失败原因。
3. 匹配/补人问题先看人数与阶段配置，再看代码调用顺序。
4. 版本问题先对齐 `version.txt`、客户端版本、管理平台推荐版本。
5. 需要人工操作时，输出逐步清单，不要假设用户已点击。
