# 任务颗粒度标准

## 1. 颗粒度判定

### 拆分的信号（命中任一就该拆）

- 一个任务里同时出现「配置/数据 + UI + 网络同步 + 业务逻辑」四件事
- 预估改动 > 400 行，或涉及 > 5 个文件
- 任务描述里出现「并且」「同时」「然后」连接两个独立关注点
- 中间产物无法独立验证（写完这一段 luacheck 不过 / PIE 跑起来崩 / 界面打不开）
- 验收方式写不出来，或者要等三件事都做完才能验

### 合并的信号（太碎了）

- 任务产出只是一个空文件 / 一个模块声明
- 「新增 Xxx 配置表」和「Xxx 配置表加字段」分成了两个任务 → 合成一个数据层任务
- 两个任务必须同时提交否则 require 失败 / 功能起不来 → 合并
- 验收方式完全一样 → 合并

### 经验分层（一个系统模块通常这么切）

```
T01  数据层：DataTable / DA / Lua Config + 读取封装   （luacheck 通过，GM/日志读表验证）
T02  网络层：服务端权威 + 远程消息 / 属性复制          （双端日志验证，无 UI）
T03  逻辑层：Manager / Service / Tool / Query          （AutoTestKit 或 GM 命令验证）
T04  UI 层：UMG/界面脚本 + 绑定 + 打开关闭             （可肉眼验证）
T05  交互层：按钮、刷新、动效、飘字                    （可肉眼验证）
T06  异常与兜底：配置缺失、消息失败、边界值
T07  联调与性能：真机、GC、DrawCall、网络裁剪、重连
```

每一层都能独立验证，这是分层的意义。不要按「文档章节」切，要按「可验证的变更单元」切。

### 任务描述五要素（缺一不可）

1. **目标**：一句话，说清做完能观察到什么
2. **改动**：文件级清单，新增/修改分开写，参照物写清楚（"参照 `Withdraw/Script/UI/Main/...lua` 第 N-M 行"）
3. **配置/网络结论**：复用还是新增，给死结论 + 理由
4. **验收方式**：具体的可操作步骤（GM 命令 / PIE 路径 / 日志关键字 / 界面点击路径），不是"功能正常"
5. **来源**：`来源: fp-xxx`（可多个）

第 5 条是原文变更同步的枢纽：策划改文档时靠它反查受影响任务，没有这条链接比对出变更也不知道改谁。一个 FP 可对应多个任务，一个任务也可跨多个 FP。

### 任务分级：L0 / L1

**L0 必须四条全中**：有明确参照物（能指出「照着 Xxx.lua 第 N-M 行改」）+ 改动 < 100 行 + 不碰框架基类、公共注册、生命周期入口 + 只有一条明显正确的路径。
典型：DataTable/DA 加字段并重导、照搬现有界面脚本改名、加注册配置、补本地化 key、加 GM 命令。

**L1 命中任一即是**：新增业务逻辑或状态机、新增/改远程消息或属性复制、动框架基类/生命周期入口、有多条路径要选（新建表 vs 复用、客户端预判 vs 等服务器）、有性能/兼容/热更风险。**标不出的按 L1。**
典型：T01 数据层（要先决策建表还是加字段）、T02 网络层、T03 逻辑层、T06 异常兜底。

比例参考：中等模块 10-20 个任务，L1 通常 4-8 个。**这个数字决定人被中断几次**，超过 10 个说明拆太细或分级太严，回头重拆。

### 复杂度分档：S 轻量 / F 完整

| 档 | 判据 | 压缩什么 |
| --- | --- | --- |
| **S 轻量** | 功能点 ≤ 4，且不新增 DataTable/DA/配置、不改网络消息、不跨模块 | `02-context.md` 只在需要决策时才写；任务合并到 3-5 个 |
| **F 完整** | 其余（含任一 L1 特征） | 四阶段全走 |

**S 档也必须建 `06-sync.md` KV。** 它是下次再来的唯一定位依据——省一行 md 换一次全量返工，不划算。

分档在 Phase A 结束时确定（此时功能点已列出），写进 `01-understand.md`。拿不准按 F。

## 2. 配置决策树

```
需求里的数据是静态的（数值、文案、掉落、解锁条件）？
├─ 是 → 目标工程现有 DataTable / DA / Lua Config / Const 有没有语义吻合的？
│       ├─ 有且字段够 → 复用，不改动。写明"复用 <资产路径或 Lua 表名> 的字段 Y"
│       ├─ 有但缺字段 → 扩表。DataTable/DA 重新导入，Const 由维护者重新生成
│       │                 （生成物不手改，重生成是人工/工具链步骤）；
│       │                 评估旧数据兼容、导表来源 CSV 是否同步、生成物是否会被覆盖
│       └─ 没有 → 新建。写明 DataTable/DA 路径或 Lua Config 文件、主键、字段、谁读
└─ 否（运行时状态、玩家进度、随机结果）
        → 不进配置表，走 PlayerDataCore / 服务端权威 / 属性复制。写明存哪里、谁同步、重连怎么办
```

本项目的静态数据落点：`Asset/Data/Table`（DataTable）、`Asset/Data/DA`（DataAsset）、`Script/Config`（Lua 配置）、`Script/Const/Generate`（生成物）。具体以目标工程为准。

常见坑：

- 把「会变的运行时状态」配进 DataTable/DA；
- 把「数值」硬编码在业务 Lua 里；
- 手改生成物（`Const/Generate/*`、`Setting/*Registry*` 等，文件头通常标明「自动生成」）；
- 直接改 `ExtendResource/*/OfficialPackage/`（升级会整体覆盖，定制放工程 `Script/` 二次封装）。
