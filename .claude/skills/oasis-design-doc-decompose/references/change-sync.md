# 腾讯文档原文变更同步

解决一个问题：**文档改了之后，之前拆好的任务怎么收敛，而不是推倒重来。**

前提（见 SKILL.md §0）：原文重取成本极低所以不落盘，但检测变更必须有基线 → **落指纹，不落原文**。指纹是几十行的功能点列表，不是几千行全文。

---

## 1. 文档注册表（`<EDITOR_ROOT>/spec/INDEX.md`）

比功能点更靠前的一层：**这个文档之前拆过没有。** 所有需求共享，每个模块一行：

```markdown
| 模块名 | 腾讯文档地址 | 别名地址 | spec 目录 | 首次拆解 | 上次同步 | 进度 |
| --- | --- | --- | --- | --- | --- | --- |
| 奖励系统 | https://docs.qq.com/doc/abc123 | | spec/reward | 2026-09-07 | 2026-09-12 | T01-T09 已实现 |
| 钓鱼图鉴 | https://docs.qq.com/sheet/def456 | | spec/codex | 2026-09-10 | 2026-09-10 | T01-T03 未开始 |
```

### 匹配规则

- **主键**：地址里的 token（`doc/<token>`、`sheet/<token>`、`slide/<token>` 等）。先去掉 `?` 后的查询参数再比对
- **模块名不是键**：它来自文档标题（见 SKILL.md §7），只用于人看，不参与判定。策划改标题时只更新这一列，spec 目录路径不动
- **别名只用于「用户确认是同一份内容」或平台明确跳转的同一文档**：分享短链、不同入口生成的同一文档地址可以补进别名列；腾讯文档的 `doc` / `sheet` / `slide` 是不同内容类型，token 不同通常就是不同文档，**不要仅凭标题相似或形态互转就并入别名**，否则会把两份需求混成一个 spec
- **同一 token 只允许一行活跃记录**。否则同一链接匹配到两个 spec 目录，下次进来选哪个没定义

### 判定优先级：先查 KV，人的明确表态优先

1. **先看 KV** —— 命中 = 同一个需求走增量对齐；未命中 = 新需求新建目录。**不要一上来就问用户**，有链接时也别再追问「是不是上次那个」
2. **用户「特别明确」说「是」或「不是」时按用户说的执行**，即使与 KV 相反。「差不多吧」「应该是」不算，仍按 KV

冲突时**改 KV，不改用户** —— KV 是记录，用户说的是事实：

| 情况 | 处理 |
| --- | --- |
| 「这就是之前那个」，但链接和 KV 存的不一样 | 新链接补进别名地址列，**沿用原 spec 目录**，不新建 |
| 「这是新需求」，但 KV 匹配上了 | 新建 `spec/<模块名>-v2/` 作为活跃行；**旧行进度标 `已被取代`**，不再参与匹配 |
| 「旧的作废，用这份新的」 | 旧行进度列标 `已废弃`，新行接管 |

每次因用户表态改 KV，在 `INDEX.md` 末尾记一行：`2026-09-12 <人>确认：新文档 xxx 取代旧 yyy，旧记录保留`。否则下次看这张表，没人知道为什么有两行相似的。

### 没有链接就不启动

链接是硬前提。没给链接时回复「需要腾讯文档链接才能开始拆解」并停止。禁止：翻工程目录同名文档替代；先拆一部分等链接再补；拿 INDEX.md 里的名字硬匹配就开工（猜错会静默跑偏）。

唯一例外：用户只给了模块名时，提示「`INDEX.md` 里 XX 模块上次用的是 <地址>，是这份吗？」，得到明确肯定才继续。这把「agent 猜测」变成「人确认」，成本一句话，防整轮返工。

## 2. 功能点 KV（`spec/<模块名>/06-sync.md`）

每个功能点一行，**两侧状态分开记**——改它们的是不同的人：

```markdown
文档: https://docs.qq.com/doc/abc123
上次同步: 2026-09-12 10:20

| FP | 功能点 | 内容摘要 | 哈希 | 文档状态 | 实现状态 | 关联任务 | 素材来源 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| fp-claim-btn | 奖励领取按钮 | 3 态：未达成/可领取/已领取 | a3f2c1 | 活跃 | 已实现 | T03, T04 | 截图：按钮三态 |
| fp-list-page | 奖励列表分页 | 每页 10 条，下拉加载 | b7c1d9 | 活跃 | 进行中 | T11 | |
| fp-sort | 列表排序 | 按时间和稀有度排序 | d2a7f3 | 活跃 | 未开始 | T14 | |
| fp-expire-tip | 过期提示 | 过期后灰显 | c9e4a2 | 已移除 | 未开始 | —— | |
```

- **文档状态**（策划改没改）：`活跃` / `已移除`
- **实现状态**（我们做没做）：`未开始` / `进行中` / `已实现` / `已废弃`，**由 agent 在任务过 gate 时更新**
- **素材来源**：画板 / 截图 / 表格的关键视觉描述（元素数量、关键文案、布局要点），用于补文字哈希检测不到的变更
- **判级前先核对实现状态**：拿 `04-impl/` 反查——有对应 `NN-*.md` 且已确认即 `已实现`。与表里不一致时**以 04-impl 为准**并在报告里提示。表漏更会让真 C2 被误判成 C1，代码悄悄漂移

这张表回答关键问题：**哪些功能已经落地了**——文档再变时据此决定「直接改」还是「开修订任务」。

### 建表规则

- **id 用语义 slug 不用序号**（最容易踩的坑）。用 `FP-01/02/03` 时，策划在中间插一条，后面编号全错位，会误报成「后半个文档全删了又全加」，机制当场作废
- **摘要按固定 schema 提炼**：`实体 / 行为 / 数量 / 边界值` 四段，能空就空。不抄原文；归一化同义词（「三种状态」「三态」→ `3 态`）；忽略排版措辞和不改变行为的形容词。schema 是为了让**不同会话生成的摘要尽量可复现**——自由文本必然漂移
- **哈希**对归一化后的摘要取 8 位十六进制。**它是快筛不是判决**：哈希相同 → 跳过该行详细比对；哈希不同 → agent 逐行做语义比对，判定「措辞变了 / 真的变了」并写明依据。**不许哈希一变就判 C2**，否则措辞噪声会淹没报告，人很快就不看了
- **接受可复现性上限**：不落原文就做不到 100% 确定性比对。把哈希当提示、把语义判断当依据，判定理由写进变更日志
- **移除 = 标记，不删行**：状态改 `已移除` 保留该行。能追溯「这功能什么时候被砍的」，也防策划误删后恢复时 id 对不上
- **腾讯文档未完整加载时禁止同步**：页面出现「登录腾讯文档」「正在同步内容...」或明显缺章，说明读到的不是全文；此时生成的指纹会把「没读到」误判成「被删除」。先拿到完整内容再比对

## 3. 入口流程

```
进来（拿到腾讯文档地址）
  │
  ├─ 没有腾讯文档链接？── 是 → 停止，索要链接。不许猜、不许凑合
  │
  ├─ 用户明确说了「是 / 不是」同一个需求？── 是 → 按用户说的走，并同步更新 INDEX.md
  │
  ├─ 查 INDEX.md（token + 别名地址）
  │    ├─ 未命中 → 取文档标题定模块名 → 新建 spec/<模块名>/ → Phase A 建 KV → Phase B 拆任务
  │    └─ 命中   → 增量对齐：
  │         1. 浏览器打开文档通读（确认完整加载）  2. 提功能点生成新指纹
  │         3. 与 06-sync.md 逐行比对 → diff（新增/修改/移除）
  │         4. 用「关联任务」列双向反查受影响任务（FP→T 和 T→FP）
  │         5. 按 §4 分级  6. 分级处理，更新指纹 + 变更日志
```

**对齐放在入口，不是「开工前」。** 两次会话可能隔好几天，策划早改过了；通读一遍文档的成本相对写错代码是便宜的。同一会话内连续做多个 L1 任务时不用重复完整对齐，轻量比对即可。

---

## 4. 变更分级：看实现状态，不看改动大小

| 级 | 判定 | 处理 | gate |
| --- | --- | --- | --- |
| **C0** | 不影响代码行为（错字、排版、配图、润色、章节顺序） | 更新哈希，记一行日志 | 否 |
| **C1** | 只影响实现状态为「未开始」的任务 | 改任务描述，**必须记日志**（否则两周后回看会以为任务本来就这样） | 否，下轮带一句 |
| **C2** | 影响「进行中」或「已实现」的任务 | **不动代码**，新增修订任务 + 出影响分析 | **是，强制** |

改动大但没开工 = C1；改动小但代码已写完 = C2。

---

## 5. 已实现的功能变了 → 新增修订任务，不回头改

**这是整套规则里最重要的一条。** 实现状态为「已实现」或「进行中」的 FP 变更时：

- **禁止**回头改原任务 T03 的描述、实现记录（`04-impl/`）和验收证据
- **改为新增修订任务** `T03-R1`，内容是「把 T03 从三态改成四态」

**为什么不直接改 T03**：

1. T03 的历史事实是「当时按三态实现并通过验收」，改它等于篡改历史
2. 返工量变成可见的独立单元 —— `T03-R1` 的改动量就是这次需求变更的真实成本
3. 追溯链完整：能看出这功能被改过几次、每次改了什么
4. 和 git 的追加语义一致：提交只追加，不改写

反过来直接改 T03：你永远不知道这功能被返工过，也回答不了「策划改需求让这模块多花了多少时间」。

**编号** `T<原号>-R<n>`，一次变更影响多个任务就各开一个（`T03-R1`、`T05-R1`）。用这个而不是新流水号，是为了让「这是返工不是新功能」一眼可见——**gate 时你会看得更仔细**。修订任务同样标 L0/L1，走同样的 gate，`来源` 指向同一个 FP。

实现状态为「未开始」的变更 → 直接改任务描述即可，没落地就没有历史要保留。

### C2 报告模板

```markdown
## C2 变更：需人工决策

**变更内容**
`fp-claim-btn`：奖励按钮从三态改为四态，新增「已过期」；过期后灰显不可点击，显示文案「已过期」。

**受影响任务**
| 任务 | 内容 | 实现状态 | 影响 |
| --- | --- | --- | --- |
| T03 | 按钮状态机 | 已实现 | 枚举加一项，UI 加灰显分支 |
| T04 | 按钮 UI 表现 | 已实现 | 加灰显状态 |
| T11 | 过期提示文案 | 未开始 | 描述要改（C1，一并处理） |

**选项与成本**
1. 返工：新增 T03-R1、T04-R1，约 60 行，1 个 L1 任务
2. 保留现状：记为已知偏差，四态留到下一版
3. 砍功能：回滚 T03/T04（不建议，会影响 T05）

**建议**：选 1，返工量可控且四态是核心规则，推迟会更贵。

## 验收
- 状态: 待确认
```

人改状态后才继续。选「保留现状」的要在 `03-plan.md` 标注已知偏差，别让它悄悄消失。

## 7. 时机

| 触发 | 动作 |
| --- | --- |
| 每次进来（新会话 / 新指令） | 查 INDEX.md + 增量对齐 |
| 同一会话内每个 L1 任务开工前 | 轻量比对 |
| 距上次同步 > 7 天 | 强制完整对齐 |
| 用户说「策划改文档了」 | 立即完整对齐 |
| 用户要「不定时提醒」 | 单独跑只读同步：只出报告，不动任务不改代码 |

**不做定时轮询** —— 检测到变更还是得处理，空转没意义。检查嵌进已有流程，成本几乎为零。

## 8. 易踩的坑

- **腾讯文档没加载完就比对** → 「没读到」被误判成「被删除」，整段重拆
- **同一文档的不同链接形态**（分享短链 / 不同入口）→ 判成新需求，整个重拆
- **序号 id** → 插一条功能点导致全盘误报
- **摘要抄原文** → 改个标点就报 C2，最后人不再看报告
- **删行而不是标记移除** → 历史丢失，恢复时 id 对不上
- **忘了更新实现状态** → 表上写着「未开始」，实际代码早写了，C2 被误判成 C1
- **分级只看改动大小** → 应看实现状态
- **C2 自己动手改代码 / 回头改原任务** → 绝对禁止
- **选「保留现状」不标注** → 已知偏差悄悄消失，验收阶段才暴露
- **KV 匹配上了还去问用户** → 多余，只有用户主动表态才覆盖
- **策划改了标题就新建目录** → 目录名是首次定名的快照，改名只更新 INDEX.md 列，不新建目录
- **用户说「是新需求」却沿用旧 spec 目录** → 旧记录必须保留，新建 `-v2`
- **任务没标 `来源: fp-xxx`** → 反查不了受影响任务，整个机制转不起来
- **哈希一变就判 C2** → 哈希只是快筛，必须语义比对后才定级
- **建了 -v2 却没把旧行标 `已被取代`** → 一 token 两活跃记录，匹配歧义
- **跨会话摘要措辞不同** → 按 schema 提炼，不要自由发挥
